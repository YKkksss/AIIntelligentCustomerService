# 0012 知识库独立化与多库关联（M4.7）

- 状态：已定稿（2026-10-22）
- 关联：`docs/02-architecture/adr/0018-管理后台工程取舍.md`、`docs/03-database/01-数据库设计.md` §3.6、`docs/00-planning/03-开发计划.md` 的 M4.7 段
- 触发：管理后台把知识库做成了「每个智能客服的附属配置」，同一份资料要给多个客服复用就得重复上传

## 1. 问题

现在知识库的所有权完全绑在应用上：`documents` / `chunks` 都带 `app_id`，入库、检索、清理、权限、开放接口路径全部以 `app_id` 为唯一作用域。结果是：

- 同一份《退换货政策》要给三个客服使用，就得传三遍，各自入库、各自切块、各自算向量；
- 改一处要改三处，切块复核、有效期、近重复提示全部重复劳动；
- 管理后台的「知识库」入口挂在单个客服下面，用户找不到「我的资料在哪」。

## 2. 目标

1. 知识库成为一等资源：左侧菜单「知识库」里创建、上传、切块、复核、命中测试、删除，与任何客服无关。
2. 客服（应用）只声明「关联了哪些知识库」，一个客服可以关联 0..N 个库。
3. 检索时把该客服关联的所有库合并召回、统一重排；引用与切块仍能追溯回原库。
4. 存量零丢失、零手工：现有每个应用的知识内容自动成为「<应用名> 默认知识库」并自动关联该应用。

## 3. 决策（2026-10-22 与用户确认）

| 议题 | 决定 | 理由 |
|---|---|---|
| 归属与可见性 | **平台公共**：有 `kb.read` / `kb.write` 就能在公共页看到并管理所有库 | 与「公共页面」的说法一致；企业内网场景不做库级分享矩阵，避免权限爆炸 |
| 关联数量 | **可关联多个、检索合并** | 抽出来的目的就是复用；一对一以后必然要改模型 |
| 存量迁移 | **自动建默认知识库并关联** | 现有 6 个应用的开放接口与页面行为保持不变，零手工 |
| 删除语义 | 库先置 `deleting`、异步清理，期间不可关联、不可检索 | 与应用的删除保持同一套体验（202 + `Job`） |
| 配置归属 | 切块参数下沉到库（`knowledge_bases.chunk_config`），客服侧不再持有知识库切块配置 | 一个库在多个客服间必须切法一致 |

## 4. 数据模型（迁移 `0018`）

```
knowledge_bases
  id uuid pk
  name text not null (1..100)，唯一约束 uq_knowledge_bases_name（去重靠业务提示，不阻断）
  description text
  status text not null default 'active'  check in ('active','deleting')
  chunk_config jsonb not null default '{}'
  config_version int not null default 1
  created_by uuid null fk users(id)
  created_at / updated_at

app_kb_links
  app_id uuid fk apps(id) on delete cascade
  kb_id  uuid fk knowledge_bases(id) on delete cascade
  created_by uuid null
  created_at
  pk (app_id, kb_id)

documents        + kb_id uuid not null fk knowledge_bases(id)   （回填后置 not null）
documents        app_id 保留：仍记录「最初由哪个应用上传」，仅用于展示与清理追溯
chunks           + kb_id uuid not null（冗余，供检索过滤；与 documents.kb_id 由入库流水线保证一致）
chunk_questions  + kb_id uuid not null（同上）
```

索引：`ix_documents_kb_status (kb_id, status)`、`ix_documents_kb_created (kb_id, created_at desc)`、`ix_chunks_kb_enabled (kb_id) where enabled`、`ix_chunks_kb_tsv` 沿用；`app_kb_links` 上 `ix_app_kb_links_kb (kb_id)` 仅供反查。

## 5. 迁移与回填（0018 内一次性完成）

1. 建两张新表；
2. 给 `documents/chunks/chunk_questions` 加可空 `kb_id`；
3. 为每个应用插一条 `<应用名> 默认知识库`（`chunk_config` 取该应用现有 `chunk_config`），写 `app_kb_links`；
4. `UPDATE documents SET kb_id = <该应用默认库>`，`chunks/chunk_questions` 通过 `document_id` 反查；
5. 三列改 `NOT NULL`，建索引；
6. downgrade 反向：删列、删表（不可逆数据丢失，脚本注释写清）。

Qdrant 的旧点没有 `kb_id`，向量库不在迁移里动——新增 `POST /admin/knowledge-bases/{id}/reindex-all` 与 CLI `aics-cli reindex-kb`，上线后对每个库跑一次重灌（登记 ISSUE-102）。

## 6. 检索链路

- 端口：`chunk_search` 从「按 app 查」改为「按 kb 集合查」；`RagPorts` 增加 `linked_kbs(app_id) -> list[UUID]`（由 `ChatRuntime` 提供，带 60 s 进程内缓存）。
- 一轮对话开始时解析该 Agent 的关联库集合；空集合 → 直接走「无命中」分支（不报错）。
- 关键词侧：`retrievable()` 的 `Document.app_id` 条件换成 `Chunk.kb_id.in_(kb_ids)`，时间窗条件保留。
- 向量侧：Qdrant filter 从 `app_id ==` 改成 `kb_id in (…)`（`kb_id` 建 keyword 索引），回查二次校验 `pl["kb_id"] in kb_ids`。
- 引用：`citations` 增 `kb_id` / `kb_name` 字段，前端引用卡片可显示来源库。

## 7. 权限

- 管理接口：`/api/v1/admin/knowledge-bases/...` 走平台级路由，`require_user()` + 校验「该用户至少在一个应用上拥有 `kb.read` / `kb.write`，或为超级管理员」；新增 `Authorizer.can_anywhere(user, permission)`。
- 开放接口：`/api/v1/apps/{app_id}/documents` 保留，语义变成「该应用默认知识库」；Key 的 `kb:read` / `kb:write` 作用域不变。
- 审计：`kb.create` / `kb.update` / `kb.delete` / `kb.link` / `kb.unlink` 五个新动作，`kb.document.*` 的 `target_type` 从 `document` 扩展为带 `kb_id`。

## 8. 接口（管理版）

```
GET    /admin/knowledge-bases                 列表（name/status/文档数/切块数/更新时间）
POST   /admin/knowledge-bases                 建库（name/description/chunk_config）
GET    /admin/knowledge-bases/{kb_id}         详情
PATCH  /admin/knowledge-bases/{kb_id}         改名 / 改描述 / 改切块参数（改参数不自动重建，返回需重建提示）
DELETE /admin/knowledge-bases/{kb_id}         202 + job，先置 deleting
GET    /admin/knowledge-bases/{kb_id}/documents            （复用现有 9 条文档路由的语义）
POST   /admin/knowledge-bases/{kb_id}/documents
…（文档 / 切块 / 任务 / 命中测试逐条平移到库作用域）
GET    /admin/apps/{app_id}/knowledge-bases   该客服关联的库
PUT    /admin/apps/{app_id}/knowledge-bases   全量替换关联（body: {"kb_ids": [...]}），写审计 kb.link / kb.unlink
```

旧路径 `/admin/apps/{app_id}/documents…` 保留一个版本周期：内部解析到该应用默认库，响应结构不变（登记 ISSUE-101）。

## 9. 前端

- 左侧菜单新增「知识库」（`/knowledge`）：卡片列表（名称、文档数、切块数、更新时间、状态）；「新建知识库」。
- 库详情 `/knowledge/:kbId`：沿用现有文档表格 / 上传 / 切块 / 待复核 / 任务 / 命中测试，只把 `appId` 换成 `kbId`。
- 客服配置页新增「关联知识库」多选（读 `GET /admin/apps/{id}/knowledge-bases`，写 `PUT`），并显示每个库的文档数；客服内的「知识库」页签从菜单移除，改为跳公共页。
- 调试对话的检索面板显示命中所属库名。

## 10. 不在本步

- 库级分享/只读授权（平台公共已经覆盖）；
- 跨库去重（同一文档进两个库各存一份）；
- 库模板与导入导出；
- 命中测试页面按库隔离（沿用现有页面，参数改为库）。

## 11. 风险

| 风险 | 处置 |
|---|---|
| Qdrant 旧点无 `kb_id`，上线后检索不到 | 迁移后立即跑 `reindex-all`；文档与 `scripts/` 写清顺序 |
| 检索从按 app 改成按库，隔离回归需重写 | 新增 `tests/integration/test_kb_isolation_pg.py`：跨库不可见、未关联库不召回 |
| 开放接口语义变化 | 保留旧路径并落到默认库，验收脚本覆盖「旧路径 == 新库路径」 |
| 关联关系变更后缓存不失效 | `app_kb_links` 变更时删 `kb:links:{app_id}` 进程内/Redis 缓存 |
