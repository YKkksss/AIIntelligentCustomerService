# 0013 知识库拥有文档（M4.7 ④）

- 状态：已接受（2026-10-23）
- 相关：设计讨论 0012（知识库独立化）、迁移 `0021`

## 背景

M4.7 把知识库抽成平台公共资源（`knowledge_bases` + `app_kb_links`），但文档仍挂在
`documents.app_id` 上，入库流水线也只认「某个智能客服的库」。结果是：

1. 公共知识库页只能看文档，上传仍要进某个智能客服的知识库页；
2. 检索（`chunk_search` / Qdrant）仍按 `app_id` 过滤，**客服关联了库也不生效**；
3. 一个库无法脱离智能客服存在（新库没有文档可上传）。

本地部署的项目里，知识库应当是「先有库、先有文档，再决定给哪些智能客服使用」。

## 决策

1. **知识库是文档的唯一归属方**：`documents.kb_id` / `chunks.kb_id` 为归属键，入库、
   重建、切块运营、命中测试都以 `kb_id` 定位。
2. **`app_id` 退化为「上传来源」**：四张表（`documents` / `chunks` / `chunk_parents` /
   `chunk_questions`）的 `app_id` 改为可空（迁移 `0021`）。公共页上传的文档 `app_id IS NULL`。
3. **检索按客服关联的库集合**：`app_kb_links` → `kb_ids` → `chunks.kb_id IN (...)`；
   未关联任何库时回落到旧的 `chunks.app_id = :app_id`（兼容历史与测试夹具）。
4. **公共知识库页做全部知识库操作**：上传、URL 导入、替换、重建、删除、切块编辑/新增、
   补充问题、命中测试，全部以 `kb_id` 为路径参数（`/api/v1/admin/knowledge-bases/{kb_id}/...`）。
5. **智能客服的知识库页改为聚合只读视图**：展示「关联的库 + 库内文档」，上传入口只保留
   跳转到公共页；客服侧的旧接口（`/apps/{app_id}/documents`）保留，行为不变。

## 后果

- 一个库可以同时被多个智能客服使用，文档只存一份；
- 存量数据零迁移（`0018` 已回填 `kb_id`，旧行仍带 `app_id`）；
- 检索层要新增「按库集合过滤」分支，Qdrant payload 需要补 `kb_id` 字段并支持按库过滤；
- 公共页与客服页的能力重叠，需要一份「谁负责什么」的说明（见 0012 §2）。
