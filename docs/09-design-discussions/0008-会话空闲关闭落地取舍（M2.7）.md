# 0008 会话空闲关闭落地取舍（M2.7）

- 日期：2026-10-17
- 状态：已采纳（M2.7）
- 相关：[会话生命周期与转人工 §2 / §3.4 / §3.10](../02-architecture/09-会话生命周期与转人工.md)、[ADR-0010](../02-architecture/adr/0010-会话空闲关闭与会话事件推送.md)、[M1 测试报告 §15](../06-development/08-M1端到端测试报告.md)

## 1. 背景
设计文档已经定了机制：beat 每 30 秒扫描，条件单行更新，不用"每条消息排一个 countdown 任务"。落地时还有几处细节没写，这里记录做法和理由。

## 2. 借鉴
| 做法 | 代表 | 收益 | 落地 |
|---|---|---|---|
| 定时扫描 + 乐观条件更新（compare-and-set），不用延时任务 | Zendesk / Intercom 的会话自动关闭、Kubernetes 控制器的 reconcile 循环 | 可重复执行、可并发、进程重启不丢计时 | M2.7 ① |
| 周期任务设 `expires`，过期就丢弃，不排队补跑 | Celery 文档对周期任务的建议 | worker 积压后不会一口气补跑几十轮 | M2.7 ② |
| 用数据库时钟作为扫描基准 | 常见做法 | 多台机器时钟漂移不影响判断 | M2.7 ① |

## 3. 不借鉴
- **每条消息排一个 countdown 任务**：设计文档已否决（RabbitMQ + `acks_late` 下长延迟任务可能重复或丢失，还要处理取消）。
- **Redis 分布式锁保证单实例扫描**：条件更新本身已经保证幂等，并发扫描只会让某几次更新落空，加锁没有额外收益，反而多一个故障点。

## 4. 我们的补充（全部在 M2.7 落地）
- **D1 不补发过期提醒**：扫描器停机后再恢复时，已经超过关闭时间的会话直接关闭，不先补发"即将结束"的提醒（提醒窗口限定为"已到提醒时间、未到关闭时间"）。如果补发，用户会先看到"即将结束"、紧接着就是"已结束"，提醒失去意义。
- **D2 准备阶段对会话行加锁**：`chat.service` 读会话时改用 `SELECT … FOR UPDATE`。原来的竞态是：读到 active → 扫描关闭 → 写 user 消息时报 409。加锁后只有两种结果：扫描先提交，chat 看到 closed 并自动新建会话；或扫描等 chat 写完 user 消息，此时 `last_activity_at` 已变，条件更新落空。集成测试 `test_sweep_waits_for_turn_holding_row_lock` 验证。
- **D3 配置无效时按对象回落**：已存配置不再满足校验（例如平台默认改了、或手工改了库）时，`session_config` / `handoff_config` 分别回落到平台默认 / 内置默认，并记日志。不能因为一个应用的配置坏了就停掉所有应用的扫描；单个应用出异常也只记日志、跳过，下一轮重试。
- **D4 批量上限**：每个应用每一步每轮最多处理 500 个会话（`SWEEP_BATCH`），剩下的等下一轮（30 秒后）。扫描时间因此有上限，不会拖过 beat 周期；开发机上一轮通常 < 0.1 s。
- **D5 预筛应用**：先用部分索引 `ix_conversations_active_activity` 查出"有活跃会话空闲超过 1 分钟"的应用（1 分钟是任何配置下提醒 / 关闭的最小延迟），再逐个应用处理，不必每轮遍历所有应用。
- **D6 应用删除中跳过**：`deleting` 的应用由删除流程统一以 `app_deleted` 关闭，空闲扫描不插手。
- **D7 `idle_closed` 允许空内容**：设计规定这条消息只作时间线标记、内容为空，`NewMessage` 校验为此放开。
- **D8 事件钩子**：`sweep(notify=...)` 在提醒 / 关闭成功提交后回调，M3.5 接入 Webhook 与事件流时直接使用；M2.7 只计数（`aics_idle_notice_total` / `aics_idle_closed_total`）并记日志。
- **D9 开发机实测用 Redis 作 broker**：开发机 RabbitMQ 的测试账号无法登录，真实 worker + beat 实测改用本机 Redis 作 broker（Celery 原生支持）；任务、路由、beat 表与生产一致。RabbitMQ 上的同一套实测已列入待复验清单。

## 5. 最终决策
按 §4 D1–D9 落地。
