# 0004 RAG 图单轮实现取舍（M2.3）
- 日期：2026-10-16
- 参与：开发（依据开发计划 M2.3、RAG 流程设计、意图识别设计与负责人 M2.3 任务说明）
- 相关：[RAG 流程设计](../02-architecture/03-RAG流程设计.md)、[意图识别](../02-architecture/08-意图识别.md)、[模型供应商抽象](../02-architecture/05-模型供应商抽象.md)、[M1 测试报告 §11](../06-development/08-M1端到端测试报告.md)

## 1. 背景
M2.3 交付单轮 RAG 图与 `run_rag`，并接入 M2.2 推迟的 LLM 熔断。设计文档定义了节点、状态、提示词与事件顺序，但有几处没有写死：`RagInput` 不含提示词需要的应用字段；M2.3 与 M2.4（意图识别）的边界；token 流的实现方式；熔断计什么；混合推理模型（DeepSeek）的思考开关。本文记录这些取舍。

## 2. 参考的业界做法
| 做法 | 出处 | 用法 |
| --- | --- | --- |
| 运行时依赖不放进图状态，通过运行上下文注入 | LangGraph `context_schema` / `Runtime`（v1） | `RagDeps(ports, llm)` 作为 context，状态里只放数据 |
| 节点内用自定义流推送 token，而不是全局 `messages` 流 | LangGraph `get_stream_writer` / `stream_mode="custom"` | 只有 generate 推送 delta |
| 熔断只统计"上游不健康"，调用方错误不计 | Hystrix / resilience4j `recordExceptions` / `ignoreExceptions` | 网络 / 超时 / 429 / 5xx 计失败，400 / 鉴权 / 程序错误不计 |
| 结构化短任务关闭推理，生成按需开启 | DeepSeek 混合推理模型 `thinking` 开关、OpenAI `reasoning_effort` | 分类 / 改写 / judge 固定关闭；generate 默认关闭（`rag_config.llm_thinking`） |
| 引用标号容错解析、越界删除 | Perplexity / Bing Chat 式 `[n]` 引用 | 支持 `[1][2]`、`[1,2]`、`[1、2]`、全角括号 |

## 3. 借鉴（ADOPT）
| # | 内容 | 收益 | 落地 |
|---|---|---|---|
| A1 | `RagDeps` 走 LangGraph 运行上下文，图在模块加载时编译一次 | 状态可序列化、无每请求编译开销 | M2.3 |
| A2 | generate 节点用 custom 流推送 `DeltaEvent`；`citations`、`trace` 同走 custom 流；最终状态取 `values` 流最后一帧 | 分类 / judge 的 token 不可能漏进回答流；事件顺序由节点代码决定，易测 | M2.3（设计文档 §6 原写 `messages` 流，已改） |
| A3 | 熔断按整次节点调用计数，每个模型一个进程内熔断器，参数同 §3（60 s / > 50 % / ≥ 10 次 / 30 s） | 流式调用也能熔断；只有上游故障打开熔断 | M2.3 |
| A4 | 分类 / 改写 / judge 请求 `thinking=False`；generate 按 `rag_config.llm_thinking`（默认 false） | 实测分类输出 token 减半、耗时 1.73 s → 1.09 s（分类超时默认 2 s，开思考时接近超时） | M2.3 |

## 4. 不借鉴（NOT ADOPT）
| # | 内容 | 理由 |
|---|---|---|
| N1 | `stream_mode="messages"` 取 token | 需要按节点名过滤，且分类 / judge 也是 chat model 调用；custom 流更直接 |
| N2 | LangGraph 节点级 `RetryPolicy` | SDK 已重试 2 次；分类 / judge 设计要求失败不重试（直接兜底） |
| N3 | 用 LangChain 结构化输出（`with_structured_output`）解析分类 / judge | DeepSeek JSON 模式 + 自己的 Pydantic 校验即可，并能在校验失败时取出 `rewritten_query`（§5.2.2 要求） |

## 5. 我们的补充（OUR ADDITIONS）
| # | 内容 | 落地 |
|---|---|---|
| C1 | `RagInput` 增加 `profile: AppProfile`（name / description / system_prompt / answer_style / fallback_text / language）、`handoff: HandoffConfig`、`tags`：rag 不读 apps 表，由 chat.service 组装传入 | M2.3（chat.service 在 M2.6 组装） |
| C2 | **M2.3 / M2.4 边界**：M2.3 做 `condense_classify`（JSON 模式、`IntentResult` 校验、§5.2.2 兜底链全部规则，因为路由正确性依赖它们）、路由与固定话术分支；M2.4 做 guard 规则层（敏感词、转人工词、连续拒答、寒暄完全匹配与模板）、无历史并行模式（classify ∥ retrieve）、LLM 寒暄回复、chat.service 的 `refusal_streak` 规则与意图评测用例 | M2.3 / M2.4 |
| C3 | `RagPorts` 增加 `llm`、`vector`、`reranker`；`vector=None` 只允许 `retrieval_mode=fulltext` | M2.3 |
| C4 | judge 的 `decision_reason` 枚举：`no_candidates`、`below_threshold`、`above_gray_upper`、`gray_answerable`（`judge_with_llm=false`）、`judge_llm_yes` / `judge_llm_no`、`judge_failed`；postprocess 另有 `output_filtered`、`empty_answer` | M2.3 |
| C5 | 模型注册表新增 `thinking: none | toggle`；`providers.llm.chat_model(thinking=...)` 只对 `toggle` 模型生效（映射 `extra_body.thinking`），其他模型忽略，换供应商不会因未知参数报错 | M2.3 |
| C6 | 输出检查（安全设计 §3.4）：泄露模式正则 + 与 generate 规则段落 20 字连续重合；**不**拿应用 `system_prompt` 比对（回答复述其中业务信息是正常的）；命中时整段替换为兜底话术，`answer_type=refused`，`degraded += output_filtered` | M2.3 |
| C7 | 越界引用标号只在最终 `RagResult.answer` 中删除；流式 delta 已发出无法撤回（与 M2.5 标识符护栏"只告警不改写"一致），客户端以 `end` 中的 answer / citations 为准 | M2.3 |
| C8 | 没有 `MemoryPort`（无状态请求、M2.5 之前）时，`inline_history` 取最近 `keep_recent_turns` 轮原文；MemoryPort 失败同样退化并记 `context_degraded` | M2.3（按预算裁剪在 M2.5） |

## 6. 实测（详见 M1 测试报告 §11）
20 题冒烟（12 可答 + 8 不可答，真实 DeepSeek + 百炼）：不可答 8/8 拒答；可答 11/12 带引用且引用命中期望文档与证据；唯一失败是 q26（"实验数据集一共有多少条问答对？"）被分类为 `out_of_scope` 未检索。应用描述只写客服主题（窄范围）时有 2 道知识库内问题被判超范围。思考开 / 关准确率相同，开启时每题输出 token 约翻倍（72.9 → 137.3），默认关闭。
