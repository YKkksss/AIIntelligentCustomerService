# 0007 对话接口落地与回问已记信息（M2.6）

- 日期：2026-10-16
- 状态：已采纳（M2.6）
- 相关：[意图识别](../02-architecture/08-意图识别.md)、[对话上下文管理](../02-architecture/07-对话上下文管理.md)、[会话生命周期与转人工](../02-architecture/09-会话生命周期与转人工.md)、[开放接口参考](../04-api/02-开放接口参考.md)、[安全设计](../08-security/01-安全设计.md)、[0006](0006-对话记忆落地取舍（M2.5）.md)、[M1 测试报告 §14](../06-development/08-M1端到端测试报告.md)

## 1. 背景
M2.6 把 RAG 图、记忆与会话状态接成对外的 `POST /v1/chat`（SSE）。落地时有两类问题设计文档没写到：
1. M2.5 评测暴露的已知限制：用户回问自己给过的信息（"我刚才给你的订单号是多少""你们会打哪个号码联系我"）被判成 kb_qa 拒答或 action 转人工（c04 第 42 轮、c08 第 26 轮）。
2. 对话接口本身的工程取舍：鉴权提前、断线持久化、并发、事件格式。

## 2. 借鉴（业界做法）
| 做法 | 代表 | 收益 | 落地 |
|---|---|---|---|
| 意图路由：把"关于本次对话的问题"单独成一类，交给只读会话记忆的回答器 | Rasa（slot 回显）、Dialogflow CX（session parameters）、LangGraph 记忆路由 | 回答来源清晰；不触发检索、不受知识库拒答阈值影响；不产生 [n] 引用 | M2.6 ④ |
| 记忆当作上下文注入生成器，而非证据 | ChatGPT 记忆、Mem0 | 用户事实与知识库证据分层 | 已在 M2.5（facts 注入 condense/generate） |
| SSE 首事件先回 ID、末事件给完整结果 | OpenAI / Anthropic 流式接口 | 客户端可断点处理；断线后能用 ID 查回 | M2.6 ③ |

## 3. 不借鉴
- **把事实作为证据塞进 judge / generate 的 `<context>`**（facts-as-evidence）。否决理由：
  1. 用户自述与知识库证据混在一起，judge"可答"会被用户的话撑起来，例如用户说"你们说过 30 天可退"就可能被当证据；
  2. [n] 引用语义被破坏（事实没有 chunk_id / 文档）；
  3. 知识库阈值与拒答策略对回问场景没有意义：回问是否可答取决于对话记录，不取决于检索分数；
  4. 回问轮次仍要付检索 + rerank 成本。
- **在 action 分支里顺带回答**：action 在 M3 才对接业务系统，现阶段走转人工，回问会被误转。

## 4. 我们的做法（M2.6 ④）
- 新意图 `recall`：condense_classify v2 增加定义、优先级 `human > action > recall > kb_qa > …`，并明确"要求查询 / 办理业务数据是 action，问业务规则是 kb_qa"，附一个示例。`enabled_intents` 可关闭；关闭时按通用回退变为 kb_qa。
- 回答节点 `recall_reply`（新提示词 `recall` v1）：只给 facts / summary / history 与问题，temperature 0、max_tokens 200、thinking 关；规则是只用对话记录中的信息、号码原样照抄、没有就直说并请用户再提供一次，不回答业务规则。
- 兜底：facts / summary / history 全空时直接回固定文案、不调模型；模型失败时用事实模板回复（`根据本次对话记录：订单号：…。`），`degraded += recall_llm_failed`。
- 护栏：沿用 M2.5 标识符检查，来源加上 history 与 summary，编造的号码记 `identifier_mismatch`（只告警，同 0006 D6）。
- 不计拒答：`answer_type=answer`，不增加 `refusal_streak`，不引用。
- 数据：迁移 0010 给 `messages.intent` 的 CHECK 加 `recall`；已存的 `enabled_intents` 若包含旧的六个意图则补上 `recall`（老应用默认得到新能力，自定义过子集的不动）。

### 评测（M2.5 记忆集，56 轮，预算 3000，真实 DeepSeek / DashScope）
| 指标 | M2.5 | M2.6 ④ |
|---|---|---|
| 保持率（retention） | 0.882 | **0.941** |
| 更新正确率 | 0.909 | **1.0** |
| 陷阱通过率 | 0.857 | **1.0** |
| 事实准确率 / 混淆率 | 1.0 / 0 | 1.0 / 0 |
| 回答质量 | 1.0 | 0.962（c06 第 17 轮答"15 个月内有效[1]"正确，但没出现评测要求的字面词，判分偏严） |
| 标识符误报 | 0 | 0 |

- c04 第 42 轮："根据记录，您提供的联系电话是 13987654321（您后来更正过）"；c08 第 26 轮："您本次提供的订单号是 2026101000999"；c05 第 22 轮（两个订单的陷阱）答对奶粉单。三者都没出现禁用号码。
- 更正类陈述（c01 第 6 轮、c11 第 19 轮"订单号说错了，应该是…"）现在判为 recall，回复是复述确认（"您后来更正为订单号 …"），M2.5 时是 action 转人工。复述确认对这类陈述是合理回复，保留。
- 评测脚本新增 `memory_use`：被记住的值出现在改写**或回答**里即算通过（recall 轮不改写），保持率 / 陷阱用它判；`rewrite_correctness` 口径不变（0.864）。
- 运行时 DeepSeek 时延偏高（实测 3k token 提示 1.9–2.6 s），默认 2 s 的 classify 超时导致 15–22 轮回退 kb_qa，使质量对比失真；质量评测加 `--classify-timeout-ms 6000` 隔离时延，时延另在端到端里测（见 M1 报告 §14）。

## 5. 对话接口的其他取舍（M2.6 ①–③）
- **D1 API Key 鉴权与限流从 M3.1 提前**：对话接口不能无鉴权挂出。提前的是核心：HMAC-SHA256 + pepper、12 位前缀、Redis 缓存 60 s、每分钟固定窗口 + 每日配额（键名按安全设计），Redis 故障时放行（fail-open）。管理后台的密钥界面、`last_used_at`、IP 白名单仍在 M3.1。
- **D2 不提供创建 / 关闭会话接口**：开放接口参考没有定义；不带 `conversation_id` 的对话请求即创建会话，关闭由 M2.7 空闲清扫负责。已关闭会话再发消息会开启新会话（会话生命周期 §3）。
- **D3 每轮独立 asyncio 任务 + 队列**：客户端断线不影响持久化；生成已完成后取消不再标记中断；尚未产出内容就断线时落一条 `decision_reason=client_disconnected` 的助手消息，保证 user/assistant 成对。
- **D4 同一会话不加轮次锁**：计数与状态在行锁下更新，并发测试通过；两轮并发时各自独立回答（与人工客服并发收消息一致）。
- **D5 `end` 事件附带完整 `answer`**：便于不拼 delta 的客户端；与 OpenAI 的最终消息一致。
- **D6 请求 `metadata` 只在新建会话时写入**：避免后续轮次覆盖首轮上下文。
- **D7 服务时间、Webhook、事件推送在 M3.4 / M3.5**：转人工轮次本期只把会话置为 pending 并落 system 消息。

## 6. 最终决策
采纳 §4（recall 意图 + 记忆回答器），否决 facts-as-evidence；§5 D1–D7 按上述落地。
