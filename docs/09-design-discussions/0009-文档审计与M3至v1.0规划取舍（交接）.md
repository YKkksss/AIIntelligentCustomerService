## 2. 借鉴
| 做法 | 代表 | 收益 | 落地 |
|---|---|---|---|
| 事务内 outbox：业务状态与事件在同一事务写入，提交后再发布 | microservices.io Transactional Outbox、Stripe Events | 状态变化和事件不会一个成功一个丢失；事件可补发、可重放 | M3.5（ADR-0016） |
| 投递记录 + 退避重试 + 手动重发 + 接收方按事件 ID 去重 | Stripe / GitHub Webhooks | 至少一次投递，运维可追查 | M3.5 |
| 重试靠数据库里的 `next_attempt_at` 加定时扫描，不靠长 countdown | Sidekiq retry set、Stripe 重试队列 | RabbitMQ 默认 `consumer_timeout` 为 30 分钟，worker 持有 30 分钟后执行的 ETA 消息会被断开通道；DB 扫描没有这个问题 | M3.5 |
| `Idempotency-Key` + 请求体哈希 + 24 小时缓存 | Stripe | 客户端重试安全 | M3.2 |
| 横切能力（鉴权、权限、审计）在 core 定义 Protocol，由业务模块实现、入口注入 | 已有的 `core.security.Authenticator` 做法、端口与适配器 | 业务模块之间保持独立（import-linter 合同不变） | M4.1（ADR-0017） |
| refresh token 轮换 + 复用检测（旧 token 再次出现即吊销整条链） | OAuth 2.0 Security BCP（RFC 9700） | 后台会话被盗时能发现 | M4.1 |
| 前端类型由 OpenAPI 生成 | openapi-typescript | 前后端字段不会漂移 | M4.1 |

## 3. 不借鉴
- **Redis Streams 作为事件的唯一存储**：共享 Redis 有 ACL 与内存上限，持久化策略不归我们管，事件可能被淘汰；PG 已经是事实来源，Redis 只做实时通知。
- **纯 pub/sub、不落库**：断线期间的事件无法补发，`Last-Event-ID` 形同虚设。
- **CDC（Debezium 等）做 outbox 转发**：组件太重，服务器只有约 1.5 GB 可用内存。
- **引入 `sse-starlette`**：现有手写实现已覆盖心跳、断开检测与事件顺序，并有测试；再引入一个依赖没有收益。
- **后台改用 session + cookie**：设计已定 JWT，前后端分离、同一网段，保持不变。
- **v1 做租户层（tenant → app）**：范围定义已放在 v2；v1 继续以 `app_id` 隔离 + 应用级 RBAC，表结构不预留 tenant 列（v2 用迁移添加，数据量小）。

## 4. 我们的补充（决策清单）
| # | 决策 | 理由 | 落地 |
|---|---|---|---|
| D1 | 文档分两类：设计文档描述 v1 **目标形态**；[实现现状与代码地图](../00-handoff/02-实现现状与代码地图.md) 是"现在有什么"的唯一来源。设计文档中尚未实现的部分标注里程碑 | 避免接手者把规划当成现状 | 本次 |
| D2 | 新增 `conversation_events`（M3.5 迁移 `0012`）：所有会话事件（eval 渠道除外）落库，`seq` 由 `UPDATE conversations SET event_seq = event_seq + 1 RETURNING event_seq` 分配；提交后 `PUBLISH aics:conv:{id}`；SSE 先按 `seq > Last-Event-ID` 补发再订阅；保留 7 天 | 见 ADR-0016 | M3.5 |
| D3 | `webhook_deliveries` 与事件一对一（`id` = 事件 ID），新增 `event_id` 外键；首次投递在提交后立即入队，失败后写 `next_attempt_at`，由 beat 任务 `aics.webhook_retry_sweep`（每 10 秒，`FOR UPDATE SKIP LOCKED`）重新入队 | 避免 30 分钟 countdown 与 RabbitMQ `consumer_timeout` 冲突；重试可见、可手动重发 | M3.5 |
| D4 | import-linter：业务模块之间的 forbidden 合同只约束**直接**依赖；`handoff` 允许依赖 `apps`。`stats` 的聚合查询可以只读地直接使用 `db.models`（不 import 其他模块），这是唯一的"跨模块读表"例外 | 见 ADR-0017 | M3.4（改合同）、M4.6 |
| D5 | 权限与审计用 core 端口：`core.security.require_perm(perm)` 委托给 `app.state.authorizer`（`modules.auth` 实现）；`core.audit.AuditSink.write(session, entry)` 由 `modules.audit` 实现，**在业务事务内**写入 | 与已有 `Authenticator` 同一模式，业务模块不 import auth / audit；审计与业务变更原子提交 | M4.1 |
| D6 | 管理接口按模块放在 `modules/<m>/admin_router.py`，统一挂载 `/api/v1/admin`；开放接口在 `modules/<m>/router.py` | 一个模块的 HTTP 面集中在模块内，main 只负责注册 | M3.2 起 |
| D7 | OpenAI 兼容的无状态请求：每次新建 `channel=openai` 会话，本轮结束即关闭，`close_reason` 新增 `stateless`（M3.3 迁移 `0011`） | 否则每个无状态请求都会在 10 分钟后产生空闲提醒和关闭事件，白白写库 | M3.3 |
| D8 | 上传：新增依赖 `python-multipart`；按块读取并累计大小，超过 `AICS_UPLOAD_MAX_MB` 立即 `413 FILE_TOO_LARGE`，不先整体读入内存 | FastAPI 的表单解析需要该依赖；服务器内存紧 | M3.2 |
| D9 | 幂等键存 Redis：`aics:idem:{key_id}:{idem}` → `{state, body_sha256, status, response}`，`SET NX EX 86400` 占位；Redis 故障时**放行**（上传仍有 `content_hash` 去重兜底，只记 warning） | 与限流的"Redis 故障放行"一致；不让共享 Redis 成为单点 | M3.2 |
| D10 | 服务时间计算用 `zoneinfo`，并新增依赖 `tzdata`（Windows 上没有 IANA 时区库） | 开发机是 Windows | M3.4 |
| D11 | Webhook 签名密钥用 `cryptography` 的 Fernet 加密（新增依赖）；`AICS_DATA_ENCRYPTION_KEY` 已在配置中必填 | 签名需要原文，不能只存哈希 | M3.5 |
| D12 | 后台登录：PyJWT（HS256）+ argon2-cffi；refresh token 的 `jti` 存 Redis 白名单（`aics:rt:{user_id}:{jti}`，TTL 7 天），每次刷新轮换，旧 `jti` 再次使用即吊销该用户全部 refresh；登录按 IP 10 次/分钟 | 安全设计 §1 与 RFC 9700 | M4.1 |
| D13 | 前端：`openapi-typescript` 生成类型；POST SSE 用 `@microsoft/fetch-event-source`；单元测试用 Vitest，覆盖 `src/api`、`src/stores`、`src/utils`、`src/composables`，门槛 80%（不含 `.vue` 视图）；Playwright 只做里程碑冒烟 | 后端覆盖率规则延伸到前端逻辑层；视图测试成本高、收益低 | M4.1 起 |
| D14 | 代码注释、docstring、标识符用英文；文档、提交信息用中文（Conventional Commits） | 大老板常设规则 | 全程 |
| D15 | 测试报告：`08-M1端到端测试报告.md` 保留为 M1–M2 报告；M3 起每个里程碑一份 `docs/06-development/1N-M<k>测试报告.md`（M3 = `10-M3测试报告.md`，M4 = `11-…`，依此类推） | 单文件已 40 KB，继续追加不利阅读 | M3 起 |
| D16 | `/metrics` 只在 API 进程用 prometheus-client 暴露（单 uvicorn 进程，不用 multiprocess 模式）；队列长度由 API 用 kombu 被动声明（`passive=True`）读取消息数；worker 侧计数器写日志，不单独暴露 | 不需要 RabbitMQ 管理接口账号，也不需要 pushgateway | M6.3 |
