# 0010 切块级运营与重建保留规则（M4.3b）

> 日期：2026-10-21 ｜ 关联：[设计讨论 0001](0001-知识库切块与检索设置-参考Dify.md)、[设计讨论 0003](0003-检索设置与切块补充问题落地（M2.2b）.md)、[M4.3b 计划](../00-planning/03-开发计划.md)

## 1 背景

M4.3 已经让管理员能看切块、禁用切块、复核被注入检测标记的切块，但**不能改一个切块**。运营里常见的情况是：自动切块把两段话切错、某个切块里有错别字、某个切块需要补一句业务口径。这些改动如果只能靠「改原文件再重建」，代价高且会丢掉人工调过的补充问题。

同时，知识库缺少三件运营基础设施：

1. **命中测试页面**（后端 `KnowledgeService.hit_test` 在 M2.2b 就有了，只有脚本能调）；
2. **补充问题管理页面**（`chunk_questions` 表与 `add/list/delete/reattach` 在 M2.2b 已有，没有 HTTP 入口）；
3. **入库近重复提示**与**文档有效期**（同一份制度上传两遍、过期制度仍在答）。

## 2 决策

### 2.1 切块来源与重建保留（核心决策）

`chunks.source` 取 `parsed`（解析自动切）、`manual`（人工新增）、`edited`（人工改过正文）。

**重建（reindex / 替换文件 / 改切块参数）时：**

- `parsed` 切块：全量重建、旧构建号清理。
- `manual` 切块：**保留并迁移到新构建号**（`index_version` 改成新号，ordinal 排在新切块之后），向量点同步改 payload 的 `index_version`/`ordinal`。
- `edited` 切块：按**正文哈希**在新构建的切块里找同一段文本：
  - 命中 → 新切块标记为 `edited`，`manual` 的正文与复核状态一并带过去；
  - 未命中 → 该切块**降级为 `manual`**（正文保留、新构建号），并在文档上留一条提示（`chunks` 的 `flag_reason` 记 `rebuild_unmatched`）。

理由：重建的输入是原文件，人工改动无法从原文件推出来；直接丢弃人工成果等于每次重建都把运营工作清零。降级而非丢弃，是为了「宁可多留一个人工块，也不要静默消失」。

### 2.2 单切块编辑只重算该切块

编辑正文时只做三件事：重算 `search_text`（词典分词 + 标题拼接）、重算 `tokens`、重算该切块的向量点（`upsert_chunks` 单点覆盖）。**不重建文档、不动其他切块的向量**，所以「编辑一个切块后其他切块向量不变」是可验证的验收项（比较 Qdrant 点向量）。

改标题（`heading_path`）同理：标题参与 `_embed_text_for` 的拼接，也要重算该点。

### 2.3 可检索条件加时间窗

可检索条件在 `backend/src/aics/modules/knowledge/chunk_search.py` 的 `retrievable()` 里是唯一实现（关键词、向量 PG 回查、对账计数都走它）。新增：

```sql
AND (documents.effective_at IS NULL OR documents.effective_at <= now())
AND (documents.expires_at IS NULL OR documents.expires_at > now())
```

**Qdrant 不存时间**：向量库只负责召回，时间过滤放在 PG 回查（`fetch_chunks`）这一步。这样过期文档不需要定时任务去同步向量库，代价是过期文档的向量点仍会在候选里出现再被丢弃——召回率不受影响，只是浪费一点候选名额。若将来候选常年被过期文档占满，再在 M4.6b 的向量对账里按 `expires_at` 定期删除。

### 2.4 近重复提示用 SimHash，只提示不阻止

入库时对解析出的正文算 64 位 SimHash，存 `documents.simhash bigint`。新文档入库前与同应用已有文档比较海明距离：

- ≤ 3：判定为近重复，在入库结果里返回 `duplicates: [{document_id, title, distance}]`，前端提示「与已有文档高度相似」，**不阻止入库**；
- 同 `content_hash`（完全相同）仍按既有逻辑直接 422/去重。

选 SimHash 而不是 minhash/embedding：不需要额外模型调用（预算 0 元）、64 位足够区分「改几句话」与「不同文档」、距离阈值有公开经验值（≤3 近重复、>10 不同）。

### 2.5 补充问题的重建迁移沿用 0003

`chunk_questions` 的重建迁移在 M2.2b 已实现（按 `anchor_hash` 匹配新切块，失配转 `pending`）。M4.3b 只补 HTTP 管理入口，不改迁移算法；`manual` 切块迁移时问题点跟着切块一起走（切块 id 不变，无需重挂）。

## 3 影响与取舍

- **接口面**：`PATCH /chunks/{id}` 扩 `text`/`heading_path`，新增 `POST /documents/{id}/chunks`（手工新增）、`GET/POST/DELETE /chunks/{id}/questions`（补充问题）、`GET /documents/duplicates`（近重复查询）、`PATCH /documents/{id}` 扩 `effective_at`/`expires_at`。全部带 `response_model`（ISSUE-86 之后的新接口一律带）。
- **审计**：`kb.chunk.create`、`kb.chunk.update`、`kb.chunk.delete`、`kb.question.create`、`kb.question.delete`、`kb.document.update`（有效期变更并进 `diff`）。
- **覆盖率的代价**：切块编辑路径要覆盖「编辑 → 检索立即返回新正文」「其他切块向量不变」「过期文档不检索」「SimHash 距离阈值」「manual 切块重建后保留」五类用例。
- **风险**：`edited` 匹配用正文哈希，正文重复时按最近 ordinal 匹配，可能把改动挂到另一份同文切块上——这是「可接受的不精确」，由前端提示人工确认。

## 4 遗留

- 过期文档的向量点清理策略（当前只靠 PG 过滤）→ 记入问题清单，M4.6b 向量对账时评估。
- `manual` 切块的 ordinal 排序规则（追加到末尾）可能让「原文顺序」与「切块顺序」不一致，命中测试页面按 ordinal 展示时需注明。
