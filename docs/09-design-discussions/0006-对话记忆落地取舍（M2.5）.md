# 0006 对话记忆落地取舍（M2.5）

- 日期：2026-10-16
- 状态：已采纳（M2.5）
- 相关：[对话上下文管理](../02-architecture/07-对话上下文管理.md)、[0002](0002-对话记忆方案（参考业界分层记忆）.md)、[ADR-0014](../02-architecture/adr/0014-对话记忆-关键事实默认开启与版本化.md)、[RAG 流程设计 §4](../02-architecture/03-RAG流程设计.md)、[M1 测试报告 §13](../06-development/08-M1端到端测试报告.md)

## 1. 背景
0002 定下了分层记忆（事实 + 滚动摘要 + 近期原文 + 回查），ADR-0014 定下了事实默认开启与版本化。M2.5 落地时又遇到几个设计文档没有写到的问题，这里记录做法和理由。

## 2. 决定

### D1 memory 与 rag 之间的适配器放在 `modules.chat`
分层契约规定 memory 不能 import rag，rag 也不能 import memory / db。`rag.ports.MemoryPort` 用 rag 自己的类型（`ContextRequest` / `ContextBundle`），`memory.service` 用 memory 自己的类型（`ContextQuery` / `LoadedContext`）。转换写在 `modules/chat/memory_port.py`（`MemoryPortAdapter`）：M2.6 组装 `RagPorts` 的正是 chat.service，放在调用方最自然。其他方案：把类型提到 core（会让 core 背上业务类型）；让 memory 依赖 rag（违反分层，否决）。

### D2 过期写丢弃：压缩不得回滚更新的槽位值
逐轮 `capture_slots` 可能在第 40 轮把订单号更正为 B，而之后执行的压缩处理的是第 1–20 轮，抽到旧值 A。如果按"后写者赢"，A 会覆盖 B。规则：候选值的来源消息位置早于当前值的来源消息时直接丢弃（`stale`），同一来源消息只在置信度更高时覆盖。这与 Mem0 / Zep 的"按事实发生时间而不是写入时间判定新旧"一致（Zep 的双时间轴）。同批内多候选同键：取来源最新的，同消息取置信度高的。

### D3 乐观锁冲突重读重试，事实与摘要同事务
事实按 `version` 乐观更新，冲突或唯一约束（并发 ADD）时重读重试最多 3 次（`MAX_RACE_RETRIES`），PG 集成测试 10 并发写同键恰好 1 次 ADD、history 连续。压缩每一批在同一事务里写入 `summary_version + 1` 与对账结果；版本冲突整批回滚，事实与摘要不会出现一半新一半旧。

### D4 压缩分批逐批提交
超过 `COMPACT_BATCH_TOKENS`（8000）的溢出按从旧到新分批，**每批一个事务**。中途失败时已提交的批次保留（覆盖范围前进、版本递增），下次从断点继续；替代方案"全部批次一个事务"在第 N 批失败时要整体重做，长对话中更容易一直失败。

### D5 每个键只存一个当前值（第二个订单只在摘要里）
`conversation_facts` 以 `(conversation_id, key)` 唯一。用户在一段对话里讨论两个订单时，`order_no` 只保留最近确认的一个，另一个只在摘要的 `confirmed_info` 里。评测 c05 专门设了这个陷阱，3 个预算都没有混淆。多值事实（`order_no[]`）需要改表结构和注入格式，等真实会话样本证明有必要时再做（M5）。

### D6 标识符护栏只告警不阻断
回答已经流式发出，事后改写不可行；阻断会把正常的"您的订单 2026… 已签收"误伤成拒答。只记 `degraded += identifier_mismatch` 与计数，留给会话日志与 M6 告警。比较时去掉连字符与空格；日期样式与少于 6 位数字的串不算标识符，以免把"2026-10-16"或型号当订单号。评测 56 轮零误报。

### D7 进程内指标、`compact_now` 不写 jobs
`/metrics` 导出在 M6.3，M2.5 先用 `core.metrics` 进程内计数（名称、标签与将来的 Prometheus 指标一致）。调试"立即压缩"的 `jobs` 行属于 M4 管理后台，M2.5 只提供同步的 `compact_now`。

### D8 回查与 `messages.search_text` 重新分词推迟到 M5
对话上下文管理 §14 把回查（消息向量化、`memory.recall`）放在 M5，`enable_history_recall` 默认 false；`search_text` 随 `custom_dict` 重算只在回查用到时才有意义，跟回查一起做。M2.5 的上下文组装为 `recall` 预留了 usage 字段（恒为 0）。

### D9 评测由脚本驱动轮次顺序
`chat.service` 在 M2.6。评测脚本按 M2.6 的顺序调用（落 user → run_rag → 落 assistant → capture_slots → maybe_compact），并以 `run_mode=eval` 同步压缩，避免依赖 worker。固定闲聊轮直接写入历史，只让需要检查的轮次走真实模型，既保证对话长度真实，又把费用控制在约 1.5 元。

### D10 `history_token_budget` 保持 3000
3000 / 8000 / 16000 的回答质量、事实准确率、混淆率、更新正确率持平，保持率差 1 条（改写措辞）。3000 平均提示词少 16%，长对话少 46%。按"无显著差异取最便宜者"保持 3000（详见 M1 报告 §13）。代价是压缩更频繁（11 段对话 9 次，8000 档 2 次），但压缩是异步的，可以配便宜的 `summary_model`。

## 3. 已知限制 / 待定项
- 回问已记信息的元问题（"你们记的我的订单号是多少"）由知识库问答管线拒答或转人工：facts 正确但不直接回答。M2.6 / M5 再评估是否加事实直答。
- 压缩抽取的 `other:*` 事实会收进闲聊中提到的事项，受 300 token 上限约束；真实样本复核后再决定是否收紧抽取提示词。
- condense_classify 2 s 超时偶发（首轮评测 10 次、复跑 0 次），超时时本轮槽位要等压缩阶段才写入；关注 M2.6 首 token 与超时率。
- 服务器复验：真实 worker 消费 `context` 队列、Redis ACL 允许 `EVAL`、真实会话样本复核预算（待复验清单）。
