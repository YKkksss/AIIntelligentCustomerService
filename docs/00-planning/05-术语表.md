# 术语表

| 术语 | 解释 |
|---|---|
| 应用（App） | 一个客服机器人。拥有自己的知识库、配置、API Key、会话。所有数据按 `app_id` 隔离 |
| 文档（Document） | 上传到某个应用知识库的一份资料（文件或网页） |
| 切块（Chunk） | 文档切成的小段文字，是检索的最小单位 |
| 标题路径（heading_path） | 切块所在的章节层级，如 `售后政策 > 退货 > 时效` |
| 向量化（Embedding） | 把文字变成一串数字（向量），意思相近的文字向量也相近 |
| 向量检索 | 用问题的向量找最相近的切块向量（Qdrant） |
| 关键词检索 | 按词语匹配查找（PostgreSQL 全文检索 + jieba 分词） |
| 混合检索 | 两种检索结果合并，互补长处 |
| RRF | Reciprocal Rank Fusion，按排名融合多路检索结果：`score = Σ 1/(k + rank)`，k=60 |
| 重排序（Rerank） | 用专门的模型对候选切块逐个和问题打相关性分，重新排序 |
| 问题改写（Condense） | 把"那它呢？"这类依赖上下文的追问改写成完整独立的问题 |
| 可答性判断 | 判断检索到的内容是否足以回答，决定生成、拒答还是转人工 |
| 转人工（Handoff） | 告诉调用方"这个问题需要人工处理"，由接入方系统接管 |
| SSE | Server-Sent Events，服务器逐段推送文本，实现"打字机"效果 |
| LangGraph | 用"节点 + 边 + 状态"编排 LLM 流程的框架 |
| Celery | Python 后台任务框架；RabbitMQ 作为消息代理（broker） |
| vhost | RabbitMQ 的虚拟主机，相当于独立的命名空间 |
| tsvector | PostgreSQL 全文检索用的分词结果类型 |
| 评测集 | 一组"问题 + 期望答案 / 期望命中文档"，用于量化准确率 |
| ADR | Architecture Decision Record，架构决策记录 |
| 意图（Intent） | 对用户问题的分类：`kb_qa`、`chitchat`、`human`、`out_of_scope`、`action`、`clarify`，规则层另有 `blocked`（见意图识别） |
| 意图来源（intent_source） | `rule` 规则层命中；`vector` 向量快速通道命中；`llm` LLM 分类结果被直接采用；`fallback` 由兜底链产生或意图识别关闭 |
| 槽位（Slot） | 意图分类时从问题中抽取的结构化信息，v1 键为 `order_no`、`product`、`phone`，与关键事实同名 |
| 关键事实（Facts） | 按会话保存的结构化事实（`conversation_facts`，默认开启），压缩时抽取并每轮从槽位写入，带类型 / 重要度，更正时旧值进入 `conversation_fact_history`；每轮固定注入 |
| 滚动摘要 / 压缩（Compaction） | 把超出预算的早期对话合并成结构化摘要，原文不删；队列 `context` 异步执行 |
| 记忆模块（aics.memory） | 负责会话上下文组装、压缩、事实、会话内回查的领域库；rag 通过 `MemoryPort` 接口调用 |
| RagResult | rag 图的唯一输出（回答、answer_type、意图、引用、提示词版本等），由 chat.service 落库 |
| RunMode | rag 图运行模式：`online`（对外）/ `debug`（调试）/ `eval`（评测），只控制压缩同步与否、trace 输出、会话渠道与统计 |
| answer_type | 回答类型：`answer`、`refused`、`handoff`、`error`（`error` 只出现在消息记录中） |
| 提示词版本（prompt_version） | 提示词文件 front-matter 中的 `version`；每条回答与每次评测都记录 |
| 构建号（index_version） | 文档每次入库/替换/重建生成的新版本号；只有生效构建号的切块可检索，切换在一个事务内完成 |
| 待复核切块（flagged） | 入库注入检测命中的切块，复核通过前不参与检索 |
| 模型注册表（AICS_MODELS） | 平台可用模型清单（名称、类型、上下文窗口、价格），应用只能选择其中的模型 |
| 会话关闭 | 会话空闲超过应用 `idle_close_minutes`（默认 10 分钟）后 `status=closed`，关闭前按 `idle_notice_before_minutes`（默认 1）发提醒；再发消息自动新建会话 |
| 转人工状态（handoff_status） | `none` → `pending`（已请求）→ `accepted`（坐席接入）→ `released`（坐席结束，AI 恢复） |
| 转人工结束原因（handoff_end_reason） | 进入 released 的原因：`agent` / `admin` / `queue_timeout`（排队超时）/ `offline`（非服务时间）/ `accepted_idle`（接入后无消息） |
| 待回访（needs_callback） | 排队超时或非服务时间转人工的会话，需人工事后联系用户；后台列表处理 |
| 服务时间（service_hours） | 应用可选的人工服务周计划 + 时区；未配置 = 7×24 |
| handoff_ai_mode | 转人工后坐席接入前的 AI 行为：`continue` 继续回答 / `wait` 停止并回复等待话术 |
| 出站 Webhook | AICS 以固定 JSON 格式、HMAC-SHA256 签名推送到接入方地址的会话事件（转人工、人工消息、空闲提醒、关闭） |
| 会话事件流 | `GET .../conversations/{id}/events` SSE 长连接，实时推送与 Webhook 相同的事件 |
| reply_by | 对话响应中本轮回复来源：`ai` / `system` / `none` |
| 消息角色 | `user`、`assistant`（AI）、`human_agent`（人工坐席）、`system`（系统话术，`kind` 区分类型） |
| scope / RBAC 权限 | API Key 的 scope（`chat`、`kb:read`、`kb:write`、`handoff:write`）与后台用户的 RBAC 权限（`app.read`、`kb.write` 等）是两套独立命名 |
| AppScopedRepository | 所有带 `app_id` 表的 repository 基类，强制第一个参数为 `app_id` 并自动过滤 |
| 每日统计（app_daily_stats） | beat 任务按应用按日聚合的统计表，仪表盘只读此表，不含调试与评测渠道 |
