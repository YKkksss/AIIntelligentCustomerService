## M3 开放接口（v0.4.0）
目标：第三方系统只靠 API Key 就能完成接入：对话（原生 + OpenAI 兼容）、知识库维护、转人工与坐席、事件推送、反馈。M3 不做任何页面。

### M3.1 API Key 收尾：`last_used_at`、IP 白名单、隔离测试
- **目标与模块设计**：`modules.apikeys` 已有生成 / 校验 / 吊销 / scope / 限流 / CLI（M2.6）。补：
  - ① `last_used_at`：鉴权成功时 `HSET aics:keyuse {key_id} {unix_ts}`（不写库）；beat 任务 `aics.flush_key_usage`（每 60 秒，maintenance 队列）`HGETALL` 后 `HDEL` 已读字段，批量 `UPDATE api_keys SET last_used_at = greatest(last_used_at, :ts)`。
  - ② `ip_allowlist`：Key 带白名单时，客户端 IP 不在任何 CIDR 内 → `403 IP_NOT_ALLOWED`。客户端 IP 取 `request.client.host`；只有当它属于新配置 `AICS_TRUSTED_PROXIES`（逗号分隔 CIDR，默认空）时才取 `X-Forwarded-For` 最右侧的非可信地址。
  - ③ 隔离测试集 `tests/integration/test_isolation_pg.py`：A 应用 Key 访问 B 应用的对话、消息、（M3.2 起）文档 → 一律 404；以后每个新开放接口都往这个文件加用例。
- **数据与接口变更**：无迁移（列已存在）。新环境变量 `AICS_TRUSTED_PROXIES`（写入配置文档与 `.env.example`）。`Principal` 增加 `client_ip`。
- **实现要点与坑**：
  - 缓存的 Key 记录要带上 `ip_allowlist`，否则每次都查库；吊销时已有缓存删除逻辑，白名单修改（M4.5）也要删缓存。
  - `HGETALL` + `HDEL` 之间的新写入会被 `HDEL` 删掉。用 Lua 脚本原子"读出并删除"，或改成按分钟分桶（`aics:keyuse:{yyyymmddHHMM}`，读完整个桶再 `DEL`）——推荐分桶，不需要 Lua。
  - Redis ACL 只允许 `aics:*`，不能用 `KEYS`；分桶键名可以直接算出来。
- **测试**：单元——CIDR 匹配（IPv4 / IPv6 / 非法地址）、可信代理解析（无代理头、多级代理、伪造头）、分桶键计算；集成——flush 后 `last_used_at` 更新且单调递增；隔离用例。
- **演示与验收**：用 CLI 建一个带 `--ip 10.0.0.0/8` 的 Key（本步给 `aics-cli apikey create` 加 `--ip` 参数，可重复），本机调用得到 403；去掉白名单后 200，1 分钟内 `last_used_at` 有值。错误 Key 401、过期 / 吊销对应错误码、超限 429 带 `Retry-After`（M2.6 已测，回归）。
- **预算**：0 元（假模型）。

### M3.2 知识库开放接口
- **目标与模块设计**：`modules/knowledge/router.py`（开放接口，前缀 `/api/v1/apps/{app_id}`），路由只做参数与响应，业务在 `KnowledgeService`。补齐 service 缺的方法：`list_documents(app_id, status, q, page, page_size)`、`get_document`、`list_chunks(app_id, document_id, page)`（只返回生效版本）、`rename_document` / `update_metadata`（PATCH，立即生效，同步 Qdrant payload 不需要——标题不在向量 payload 里，若在则 `set_payload`）。幂等中间件 `core.idempotency`（纯 Redis 逻辑，FastAPI 依赖形式）。
- **数据与接口变更**：
  - 接口见[开放接口参考 §4](../04-api/02-开放接口参考.md)：上传、URL 导入、列表、详情、切块列表、替换文件、重建、PATCH、DELETE。scope `kb:read` / `kb:write`。
  - 无迁移。新依赖 `python-multipart`。
- **实现要点与坑**：
  - 上传：`UploadFile` 按 1 MB 块读取并累计，超过 `AICS_UPLOAD_MAX_MB` 立即 413，不要 `await file.read()` 整体读入（服务器内存紧）。扩展名白名单 + 魔数校验已在 `ingest.parsers`；在接口层先做扩展名快速拒绝（400 `UNSUPPORTED_FILE_TYPE`）。
  - 幂等（[接口规范 §7](../04-api/01-接口规范.md)，设计讨论 0009 D9）：`SET aics:idem:{key_id}:{idem} {"state":"processing","sha":…} NX EX 86400`；成功后覆盖为 `{"state":"done","status":202,"body":…}`；请求体哈希对 multipart 取"文件 SHA-256 + 其他字段的规范 JSON"。处理中再来 → `409 CONFLICT`；哈希不同 → `409 IDEMPOTENCY_CONFLICT`；处理失败（非 2xx）删除占位，允许重试。Redis 异常放行并记 warning。
  - `DocumentNotFoundError` 在 `ingest.service` 与 `knowledge.service` 各有一个，统一用 knowledge 的那个（错误码 `DOCUMENT_NOT_FOUND`），ingest 内部改为抛 core 的 `NotFoundError` 子类或复用。
  - 删除返回 204 后文档立即不可检索（M1.6 已有 `deleting` 逻辑）；替换 / 重建期间旧版本继续可检索。
  - 列表 `q` 用 `title ILIKE`（转义 `%` 与 `_`），不要用全文检索。
- **测试**：单元——幂等状态机（首次、处理中、相同体、不同体、失败释放、Redis 故障放行）、大小限制（刚好等于上限、超出 1 字节）；集成——每个接口的 2xx 与错误码、scope 不足 403、跨应用 404（加入隔离测试集）、同一幂等键重复上传只产生一个文档。
- **演示与验收**：按[第三方接入指南](../04-api/04-第三方接入指南.md)的 curl 示例上传 MD → 轮询到 `done` → 对话命中 → 替换 → 删除；示例原样可运行（示例有错就改示例）。
- **预算**：演示时真实向量化 1 份长文档（约 2 万字，DashScope ≈ 0.01 元）+ 5 轮对话（≈ 0.06 元），< 0.1 元。

### M3.3 OpenAI 兼容接口
- **目标与模块设计**：`modules/chat/openai_router.py`：`GET /v1/models`、`POST /v1/chat/completions`（阻塞 + `stream`）。全部经 `ChatService.start_turn`（`channel="openai"`），不另拼流程。无状态请求的历史裁剪走 `memory.context` 的无状态路径（M2.5 已有）+ 临时摘要（`openai_temp_summary`，超预算时 15 s 超时摘要，失败只裁剪）。
- **数据与接口变更**：
  - 迁移 `0011`：`CLOSE_REASONS` 增加 `stateless`（CHECK 约束重建）。
  - 接口见[开放接口参考 §3](../04-api/02-开放接口参考.md)；错误体为 OpenAI 风格 `{"error":{"message","type","code"}}`，由该 router 的异常处理器把 `AppError` 转换（只作用于 `/v1/*`，原生接口不变）。
- **实现要点与坑**：
  - 不带 `X-AICS-Conversation-Id`：新建会话、只写本轮、**本轮结束即关闭**（`close_reason=stateless`，设计讨论 0009 D7），不触发压缩、不产生空闲提醒。带头：与原生接口完全相同（关闭则自动新建）。
  - 客户端 `system` 消息忽略；`temperature` / `max_tokens` 取 `min(请求, 应用配置)`；`tools`、`functions`、`n>1` 等忽略（`n>1` 返回 1 个 choice）。
  - 流式格式：每个 `delta` → `data: {"object":"chat.completion.chunk","choices":[{"delta":{"content":…}}]}`；第一个 chunk 带 `{"role":"assistant"}`；最后一个 chunk `finish_reason="stop"` 且带 `aics` 扩展字段；然后 `data: [DONE]`。心跳用 SSE 注释行（OpenAI SDK 会忽略）。
  - `model` 与 Key 所属应用不一致 → 404 `model_not_found`。
  - `reply_by=none`（坐席已接入）时 `content=""`，`finish_reason="stop"`。
- **测试**：单元——消息列表解析（最后一条必须是 user，否则 422）、参数上限截断、chunk 序列化；集成——用官方 `openai` Python SDK（加到 dev 依赖）对 TestClient / 本地 uvicorn 做阻塞与流式调用，带头 / 不带头两种会话关联，`stateless` 会话被关闭且不被扫描。
- **演示与验收**：`openai.OpenAI(base_url=…/v1, api_key=aics_…)` 改 `base_url` 即可对话（阻塞与流式），用 10 轮长对话（历史在请求里）验证无状态裁剪生效（`context_usage` 不超预算）。
- **预算**：真实模型 2 段 × 10 轮 ≈ 0.3 元（含一次临时摘要）。

### M3.4 转人工状态机与坐席接口
- **目标与模块设计**：新模块 `modules.handoff`（`service.py`、`repository.py`、`router.py`、`schedule.py`）：
  - `HandoffService.accept / post_agent_message / release / get / list_open`；后台释放 `release(by="admin")` 在 M4.5 接页面。
  - 触发侧（`chat.service` 已在 M2.6 把 none/released → pending）：本步把"是否在服务时间"判断加进去——不在服务时间 → `released` + `offline` + 待回访 + `system/handoff_offline` 回复（`reply_by=system`）。判断函数 `handoff.schedule.in_service_hours(cfg, now)` 是纯函数，chat 调用它需要 `chat → handoff` 依赖，这会形成环（handoff → chat）。**解决**：`in_service_hours` 放在 `aics.rag.config` 旁的纯函数模块不合适（rag 不管业务时间），放在 `aics.core.schedule`（纯函数，无项目依赖）。
  - 超时扫描：`handoff.service.sweep(now)`：排队超时（§3.6）、接入后无消息超时（§3.8），条件单行更新、批量上限 500；`tasks.maintenance.idle_sweep` 改为先调 `handoff` 的 sweep 再调 `chat.lifecycle.sweep`（[会话生命周期 §3.10](../02-architecture/09-会话生命周期与转人工.md)）。
  - 先改 import-linter 合同（ADR-0017）：forbidden 合同加 `allow_indirect_imports = true`，handoff 允许依赖 apps。
- **数据与接口变更**：无新表（`conversations` 的 handoff / callback 列、`messages.kind` 的 handoff 取值在 M2.1 已建）。接口见[开放接口参考 §5](../04-api/02-开放接口参考.md)（scope `handoff:write`）。新依赖 `tzdata`。
- **实现要点与坑**：
  - 所有状态迁移都是条件更新：`UPDATE … WHERE handoff_status = :expected [AND handoff_requested_at = :seen]`，影响行数 0 → 重新读取后返回 `409 HANDOFF_STATE_CONFLICT`（`details.handoff_status`）。
  - `post_agent_message` 写 `role=human_agent` 消息要更新 `last_activity_at`、`message_count`，并清 `idle_notice_sent_at`；写消息走 `chat` 的 repository 方法（经 `chat.service` 暴露的函数，不直接 import chat.repository——规则 2）。
  - release（含排队超时）把 `last_activity_at = now()`，重新开始空闲计时（§3.4）。
  - 接入后无消息超时同时关闭会话（`close_reason=handoff_idle`）。
  - 服务时间区间右开、不跨零点；时区用 `zoneinfo.ZoneInfo`；DST 时区也要测（如 `America/New_York`）。
  - 本步只写消息与状态，**不发事件**：在调用点留 `events.emit(...)` 的位置（M3.5 接上），用 TODO 注释写清楚事件名。
- **测试**：单元——`in_service_hours`（边界、时区、多时段、未配置 = 7×24）、状态迁移表全覆盖（每个状态 × 每个动作）、continue / wait 下 pending 与 accepted 的 `reply_by`；集成（PG）——三种超时由 sweep 触发且幂等、并发 accept 只有一个成功、accept 与排队超时竞争、`handoff_queue_timeout_minutes ≥ idle_close_minutes` 保存被拒（M2.7 已有校验，回归）。
- **演示与验收**：脚本模拟坐席平台：用户说"转人工" → 坐席 `GET /handoffs?status=pending` 看到 → accept → 发人工消息 → 用户在消息列表看到 `human_agent` 消息 → release → AI 恢复回答；另演示排队超时与非服务时间。
- **预算**：演示 6 轮真实对话 < 0.1 元；其余假模型。

### M3.5 Webhook 与会话事件流
- **目标与模块设计**（ADR-0016、设计讨论 0009 D2/D3/D11）：
  - `modules/chat/events.py`：`emit(session, conv, type, data)`（事务内分配 `seq`、写 `conversation_events`、按需写 `webhook_deliveries`）与 `after_commit(...)`（`PUBLISH` + 投递任务）。接上 M2.7 / M3.4 留下的全部事件点：`handoff.requested/accepted/released/queue_timeout/offline`、`message.created`、`conversation.idle_notice/closed`。
  - `modules/webhooks/`：`payloads.py`（固定格式，[第三方接入指南 §7](../04-api/04-第三方接入指南.md)）、`signing.py`（HMAC-SHA256，`timestamp + "." + body`）、`crypto.py`（Fernet 加解密 `secret_enc`）、`service.py`（`plan_delivery`、`deliver(delivery_id)`、`redeliver`、`rotate_secret`、`send_test`）、`repository.py`。
  - 任务：`aics.deliver_webhook(delivery_id)`（context 队列）、beat `aics.webhook_retry_sweep`（每 10 秒，把 `status=pending AND next_attempt_at <= now()` 的投递重新入队，`FOR UPDATE SKIP LOCKED` + 批量 100）。
  - SSE：`GET /api/v1/apps/{app_id}/conversations/{id}/events`（scope `chat` 或 `handoff:write`）放在 `chat/router.py`，复用 `chat/sse.py` 的帧格式与 15 秒心跳。
- **数据与接口变更**：迁移 `0012`：`conversation_events`（ADR-0016）、`webhook_deliveries`（[数据库设计 §3.15](../03-database/01-数据库设计.md)，增加 `event_id` FK）。新依赖 `cryptography`。
- **实现要点与坑**：
  - `seq` 分配必须在持有会话行锁的事务里；`chat.service` 准备阶段已 `FOR UPDATE`，扫描的条件更新也锁行——emit 一定要在同一个 session 里调用。
  - 提交前不能 `PUBLISH`（订阅方回表会读不到）。做法：service 收集 `pending_notifications`，commit 成功后统一发出。
  - 投递：`httpx` 超时 5 秒、**不跟随重定向**、每次投递前用 `core.netguard` 重新校验 URL（DNS 可能变）；2xx 成功；否则 `attempts += 1`，按 10s、30s、2min、10min、30min 写 `next_attempt_at`，第 6 次失败 → `failed` 并计数 `aics_webhook_failures_total`。
  - 不要用 Celery `countdown` 做 30 分钟延迟（RabbitMQ `consumer_timeout` 默认 30 分钟，见设计讨论 0009）。
  - SSE：先 `SUBSCRIBE` 再补发，按 `seq` 去重；客户端断开要取消订阅（`finally` 里 `unsubscribe` + `aclose`）；每个连接一个 Redis pubsub 连接，注意连接池上限（开发期 20 并发够用）。会话关闭事件发出后结束流。
  - Redis ACL：`PUBLISH` / `SUBSCRIBE` 需要频道权限（`&aics:*`），写进待复验清单。
  - payload 含会话原文与事实原值，日志里只记 `delivery_id`、状态码。
- **测试**：单元——签名（与[第三方接入指南](../04-api/04-第三方接入指南.md)的 Python / JS 校验示例互通，示例代码本身也跑一遍）、退避表、payload 快照、Fernet 往返、私网 URL 被拒；集成——事件与状态同事务（回滚时没有事件）、`seq` 连续无重复（并发 10 条消息）、SSE `Last-Event-ID` 补发、投递失败重试至 `failed`、debug / eval 渠道不投递、本地 HTTP 接收端（pytest 起一个 `httpx.MockTransport` 或 aiohttp 小服务）收全流程。
- **演示与验收**：示例接收端（`scripts/e2e_m3/webhook_receiver.py`，校验签名并打印）完成 requested → accepted → 人工回复 → released 全流程；断开 SSE 后发两条人工消息，重连带 `Last-Event-ID` 补发两条；接收端返回 500 时按退避重试。
- **预算**：演示 4 轮真实对话 < 0.1 元。

- **预算**：57 条单轮 ≈ 0.4 元；阈值网格只重算分类结果（缓存 LLM 原始输出），不重复调用。

### M5.6 回答语言跟随与多语言（M2 遗留）
- **目标与模块设计**：英文提问目前用中文回答。`apps.language` 增加取值 `auto`（默认仍 `zh-CN`）：`auto` 时 generate / chitchat / recall 提示词加"用与用户问题相同的语言回答"，话术类（兜底、转人工、等待）仍用应用配置文本。语言检测用简单规则（拉丁字母占比 > 60% 视为英文），检测结果写入 trace。
- **数据与接口变更**：无迁移（`language` 是 text）；提示词 +1 版本。
- **实现要点与坑**：知识库是中文、问题是英文时检索仍用中文改写——condense_classify 提示词要求 `rewritten_query` 用知识库语言（应用 `language` 非 auto 时为该语言，auto 时默认中文）。
- **测试 / 验收**：20 题英文问题评测：回答语言正确率 ≥ 95%，回答正确率不低于对应中文版 −5 个百分点；`language=zh-CN` 应用行为不变（回归）。语言检测规则单测（中英混排、纯数字、代码片段）。
- **预算**：20 题 ≈ 0.3 元。

### M5.7 首 token 时延（M2 遗留，视服务器复测结果）
- **目标与模块设计**：先做待复验清单"M2.6 首 token 时延复测"。若服务器上 P50 仍 > 2.5 s：方案按收益排序——① 带历史时也让检索（用原问题）与 condense_classify 并行，classify 判为 kb_qa 且改写与原问题差异小时直接用并行结果（差异大则用改写结果重检索）；② classify 换更快的模型（注册表新增，`intent` 增加 `classify_model`）；③ 调 `classify_timeout_ms`。每个方案都用评测集验证准确率不下降。
- **测试 / 验收**：首 token P50 ≤ 2.5 s、P95 ≤ 5 s（服务器、非高峰、20 并发以下），准确率指标不低于 M5.5 基线。
- **预算**：两轮各 30 题 ≈ 0.8 元。

### M6.2 镜像与部署
- **内容**：`deploy/app/`：`Dockerfile.backend`（多阶段，`uv sync --frozen --no-dev`，非 root 用户，tiktoken 编码预下载进镜像）、`Dockerfile.web`（Nginx + 构建产物）、`docker-compose.yml`（[应用部署 §1](../07-deployment/03-应用部署.md) 的 5 个服务与内存上限）、`nginx.conf`（SSE 关缓冲）、`deploy/scripts/deploy.sh`（备份 → 迁移 → 启动 → 轮询 `/readyz` 60 s → 失败回滚）；`.github/workflows/release.yml`（tag 触发构建推送 GHCR、创建 Release）。
- **坑**：服务器可用内存约 1.5 GB——上线前 `free -h` 与 `docker stats` 实测；不够时 `aics-worker`（入库）不在服务器运行。迁移必须向后兼容一个版本（回滚只换镜像不回滚迁移）。部署操作会动服务器，**每一步执行前问大老板**。
- **验收**：服务器部署某个 tag，`/readyz` 全部 ok；故意失败的部署自动回滚；同时完成待复验清单中的全部服务器项，补打 `v0.2.0`–`v0.6.0` 中尚未打的 tag（或在 Release Notes 中说明合并发布）。**预算**：冒烟 < 0.1 元。

### M6.3 监控与日志
- **内容**：prometheus-client 暴露 `/metrics`（设计讨论 0009 D16，[监控与运维手册 §1](../07-deployment/05-监控与运维手册.md) 的指标清单）；`core.metrics` 的进程内计数器改为 prometheus 指标；告警规则文件（若服务器无 Prometheus，则文档化"仪表盘 + 日志告警"方案）；docker json-file 日志轮转（`max-size=20m, max-file=5`）。
- **验收**：指标可抓取；模拟 5xx 触发告警。**预算**：0 元。

### M6.4 备份与恢复
- **内容**：`backup.sh`（`pg_dump -Fc aics`、只对 `aics_` 前缀集合做 Qdrant 快照、上传文件 tar）、`restore.sh`；恢复演练一次（到 `aics_test`），记录耗时（RTO ≤ 4 h）。
- **坑**：Qdrant 是共用实例，快照与恢复只能操作 `aics_` 集合；恢复前确认目标库名，**问大老板**。
- **验收**：在 `aics_test` 恢复成功并记录耗时。**预算**：0 元。

### M6.5 压测与发布（v1.0.0）
- **内容**：k6 或 locust 脚本：20 并发对话持续 10 分钟（假 LLM 模式测系统本身 + 真实模型 2 分钟小样本）；错误率 < 1%；`SWEEP_BATCH` 在 1 万活跃会话下的单轮耗时（待复验清单 M2.7 项）；运维手册定稿；`dev` → `main`、tag `v1.0.0`、Release Notes。

- **预算**：真实模型 2 分钟 × 20 并发 ≈ 150 轮 ≈ 2 元。**理由**：发布前唯一一次真实负载验证；如超预算先用 5 并发。
