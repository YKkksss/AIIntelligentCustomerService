## 2. M3.1 ① `last_used_at`：Redis 分钟分桶 + beat 批量落库

**落地要点**：鉴权成功（限流通过后）向 `{prefix}keyuse:{yyyymmddHHMM}`（UTC 分钟桶）`HSET key_id=unix_ts` 并 `EXPIRE 900`，**不写库**；beat 任务 `aics.flush_key_usage`（maintenance 队列，每 60 秒，`expires` 55 秒）读最近 11 个桶（当前分钟只读不删，历史桶读后 `DEL`），按键取最大时间戳，用**一条** `UPDATE api_keys SET last_used_at = greatest(last_used_at, to_timestamp(:ts))` 落库。分桶让“过去的桶不可变”，因此不需要 Lua，也没有 `HGETALL`/`HDEL` 之间的丢写竞态（后续计划 §M3.1 的推荐方案）。`to_timestamp` 是必需的：`greatest(timestamptz, integer)` 在 PG 上不存在；`GREATEST` 会忽略 NULL，所以首次使用也能写入。

Redis 异常只记 `apikeys.key_usage_unavailable` 警告并放行（与限流 fail-open 一致）；鉴权失败路径不写标记。

| 层 | 用例 | 断言 |
|---|---|---|
| 单元 `tests/unit/test_keyusage.py` | `test_bucket_key_is_the_utc_minute` | `1_800_000_000` → `…202701150800`；+59 s 同桶、+60 s 进下一桶 |
| | `test_record_use_writes_one_field_with_ttl` | 每 Key 一个字段 + TTL 900，不写库 |
| | `test_record_use_swallows_redis_failure` | Redis 故障不影响鉴权 |
| | `test_merge_buckets_keeps_the_newest_and_drops_garbage` | 同键取最新、无法解析的值丢弃 |
| | `test_flush_folds_buckets_and_deletes_only_past_minutes` | 当前分钟读取但**不删除**；历史桶读后 DEL；`greatest` 不回退 |
| | `test_flush_without_buckets_never_opens_a_session` | 空桶直接返回，不建数据库会话 |

## 3. M3.1 ② IP 白名单与可信代理

**判定顺序**（`ApiKeyAuthenticator.authenticate`）：bearer → HMAC → 吊销 → 过期 → 应用绑定（跨应用 404）→ 应用禁用 → **IP 白名单** → scope → 限流 → 使用标记。白名单检查放在 scope 之前、限流之前，所以被拒请求**不消耗配额**、也不产生 `last_used_at`。

**语义**：客户端 IP 取 `request.client.host`；只有当该地址本身落在新配置 `AICS_TRUSTED_PROXIES`（逗号分隔 CIDR，默认空 = 不信任任何代理）内时，才从右往左取 `X-Forwarded-For` 中第一个非可信地址；链里出现无法解析的地址时返回 `None`（宁可不放行，也不猜）。白名单存在但客户端地址未知 → 同样 `403 IP_NOT_ALLOWED`（fail-closed）。直连（对端不可信）时请求头完全无效，伪造无效。

缓存的 Key 记录带上 `ip_allowlist`，所以命中 60 秒缓存也照样校验；`set_ip_allowlist`（M4.5 的管理接口会复用）改写后立即删除该 Key 的缓存，改严即刻生效。CIDR 校验在写入前完成（非法 → `422 VALIDATION_ERROR`，不交给 PostgreSQL 报 500），单个 IP 按 `/32`、`/128`，按掩码归一化（`10.1.2.3/8` → `10.0.0.0/8`）。

| 层 | 用例 | 断言 |
|---|---|---|
| 单元 `tests/unit/test_netguard.py` | `test_resolve_client_ip`（15 组） | 无代理头 / 多级代理 / 全可信链 / 非法地址 / 缺地址 / IPv6 与 v4-mapped；不可信对端时忽略 `X-Forwarded-For` |
| 单元 `tests/unit/test_apikeys.py` | `test_parse_ip_allowlist_normalizes`（7 组） | 空 → `None`；单 IP 补掩码；非法输入 422 且 `loc=ip_allowlist` |

| | `test_ip_allowlist_rejections`（6 组） | 白名单外、地址未知、直连伪造头、非可信对端、可信代理但客户端不在白名单、转发链非法 → 全部 `403 IP_NOT_ALLOWED` 且 `details.client_ip` |

## 4. M3.1 ③ 跨应用隔离回归集与开放接口清单守卫

隔离用例是开放接口的合并门禁（设计讨论 0009 D22）。为免“接口加了、用例忘了”，把接口清单抽成单一事实来源 `backend/tests/open_api.py`（method / path / 请求体模板），供隔离用例与守卫测试共用。

| 层 | 用例 | 断言 |
|---|---|---|
| 单元 `tests/unit/test_open_api_coverage.py` | `test_every_open_route_is_declared` | 任何 `/api/v1/apps/...` 新路由未登记 → 失败（CI 只跑非 integration，所以守卫必须在单测里） |
| | `test_declared_routes_still_exist` | 登记的接口被删掉 → 失败 |
| 集成 `tests/integration/test_isolation_pg.py` | `test_cross_app_key_is_404`（每个开放接口一行） | A 应用 Key 访问 B 应用接口 → `404 APP_NOT_FOUND` |
| | `test_cross_app_conversation_is_404_on_messages` / `…_on_chat` | A 的 Key + B 的会话 id → `404 CONVERSATION_NOT_FOUND`（不泄露资源是否存在） |
| | `test_cross_app_conversation_does_not_leak_messages` | 反向：B 的 Key 读 A 的会话同样 404 |
| | `test_own_key_and_resource_still_works` | 正向对照：自己的 Key + 自己的会话 200，保证上面的 404 来自隔离而非接口损坏 |

**实现记录**：当前 Starlette 1.8.0 把 `include_router` 后的子路由保留为 `_IncludedRouter`，`app.routes` 里拿不到 `path`；守卫改为读 `app.openapi()["paths"]`（对后续版本更稳）。这是后续要枚举路由时（如 M3.6 的 OpenAPI 整理）需要注意的坑。
