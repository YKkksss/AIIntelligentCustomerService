## 2. M3.1 ① `last_used_at`：Redis 分钟分桶 + beat 批量落库

**落地要点**：鉴权成功（限流通过后）向 `{prefix}keyuse:{yyyymmddHHMM}`（UTC 分钟桶）`HSET key_id=unix_ts` 并 `EXPIRE 900`，**不写库**；beat 任务 `aics.flush_key_usage`（maintenance 队列，每 60 秒，`expires` 55 秒）读最近 11 个桶（当前分钟只读不删，历史桶读后 `DEL`），按键取最大时间戳，用**一条** `UPDATE api_keys SET last_used_at = greatest(last_used_at, to_timestamp(:ts))` 落库。分桶让“过去的桶不可变”，因此不需要 Lua，也没有 `HGETALL`/`HDEL` 之间的丢写竞态（后续计划 §M3.1 的推荐方案）。`to_timestamp` 是必需的：`greatest(timestamptz, integer)` 在 PG 上不存在；`GREATEST` 会忽略 NULL，所以首次使用也能写入。

Redis 异常只记 `apikeys.key_usage_unavailable` 警告并放行（与限流 fail-open 一致）；鉴权失败路径不写标记。

## 3. M3.1 ② IP 白名单与可信代理

**判定顺序**（`ApiKeyAuthenticator.authenticate`）：bearer → HMAC → 吊销 → 过期 → 应用绑定（跨应用 404）→ 应用禁用 → **IP 白名单** → scope → 限流 → 使用标记。白名单检查放在 scope 之前、限流之前，所以被拒请求**不消耗配额**、也不产生 `last_used_at`。

**语义**：客户端 IP 取 `request.client.host`；只有当该地址本身落在新配置 `AICS_TRUSTED_PROXIES`（逗号分隔 CIDR，默认空 = 不信任任何代理）内时，才从右往左取 `X-Forwarded-For` 中第一个非可信地址；链里出现无法解析的地址时返回 `None`（宁可不放行，也不猜）。白名单存在但客户端地址未知 → 同样 `403 IP_NOT_ALLOWED`（fail-closed）。直连（对端不可信）时请求头完全无效，伪造无效。

缓存的 Key 记录带上 `ip_allowlist`，所以命中 60 秒缓存也照样校验；`set_ip_allowlist`（M4.5 的管理接口会复用）改写后立即删除该 Key 的缓存，改严即刻生效。CIDR 校验在写入前完成（非法 → `422 VALIDATION_ERROR`，不交给 PostgreSQL 报 500），单个 IP 按 `/32`、`/128`，按掩码归一化（`10.1.2.3/8` → `10.0.0.0/8`）。

## 7. M3.2 ② 幂等键与写接口（`0d456ec`）

**幂等键**（`core/idempotency.py`，FastAPI 依赖形式，纯 Redis）：请求头 `Idempotency-Key`（≤128 字符）→ `SET {prefix}idem:{key_id}:{key} NX EX 86400` 写占位 `{"state":"processing","sha":…}`；处理中重复 → `409 CONFLICT`；同一键但请求体摘要不同 → `409 IDEMPOTENCY_CONFLICT`；成功后把占位覆写成 `{"state":"done","status":…,"body":…}`（响应体上限 64 KB）并直接回放；非 2xx 与异常一律**删占位**，允许客户端立即重试；Redis 不可用则**放行**并记 `idempotency.unavailable` 警告（上传本身还有 `content_hash` 去重兜底，与设计讨论 0009 D9 一致）。请求体摘要：multipart 取“文件 SHA-256 + 其它字段的规范 JSON”，JSON 请求取规范化后的整体。

**写接口**（`modules/knowledge/router.py`，scope `kb:write`）：上传 `POST /documents`（202）、URL 导入 `POST /documents/url`（202）、替换 `PUT /documents/{document_id}/file`（202；内容未变 200 `{"unchanged":true}`；与其它文档重复 409 `DUPLICATE_DOCUMENT`；构建中 409 `DOCUMENT_BUSY`）、重建 `POST /documents/{document_id}/reindex`（202）、改标题与元数据 `PATCH /documents/{document_id}`（立即生效）、删除 `DELETE /documents/{document_id}`（204，立即不可检索、异步清理）。上传**按 1 MB 分块流式累加**，超过 `AICS_UPLOAD_MAX_MB` 立刻 `413 FILE_TOO_LARGE`（不把整个文件读进内存，服务器内存紧张）；扩展名先快速拒绝 `400 UNSUPPORTED_FILE_TYPE`，魔数仍由 `ingest.parsers` 判定；`metadata` 上限 8 KB、`url` 上限 2048 字符。

**用完即关**：`_Prepared.stateless`（由「请求没带 conversation_id」推出），`_execute` 的 `finally` 调 `_close_stateless`，复用 `ConversationRepository.close`（条件单行更新，天然幂等）写 `close_reason=stateless`；同时 `_after_turn` 直接返回——不压缩、不写事实、不产生空闲提醒；`idle_sweep` 只扫 `status='active'`，所以关掉之后不会再被扫到。

## 11. M3.3 ② OpenAI 兼容路由（`5a1122e`）

**两个端点**：`GET /v1/models`（只返回 Key 所属应用）、`POST /v1/chat/completions`（阻塞 + 流式同一条执行路径）。纯函数与请求模型在 `modules/chat/openai.py`，路由在 `modules/chat/openai_router.py`。

| 契约点 | 实现 |
|---|---|
| `model` | 必须等于 Key 所属应用，否则 404 `model_not_found` |
| `messages` | 最后一条必须是 `user`（否则 422）；客户端 `system` 忽略；历史取最后一条 user 之前的 `user`/`assistant`，按应用预算裁剪（超预算且 `openai_temp_summary` 时用请求内临时摘要） |
| 不可用字段 | `tools` / `functions` / `n` 忽略（`n>1` 只回 1 个 choice） |
| `temperature` / `max_tokens` | 只能**收窄**：`min(请求, 应用配置)`；其它键忽略（`model_copy` 会绕过校验，先在 `clamp_overrides` 里过滤） |
| 无 `X-AICS-Conversation-Id` | 新建 `channel=openai` 会话、只写本轮、本轮结束即关（`close_reason=stateless`），响应回带 `aics.conversation_id` 但不作为下次历史 |
| 带该头 | 值必须是本应用会话 id，否则 404 `conversation_not_found`；会话已关闭 → 自动新建并回填 `aics.previous_conversation_id` |
| 应答形态 | `chat.completion`（`chatcmpl-…`、`usage`）+ `aics` 扩展（`message_id`/`conversation_id`/`previous_conversation_id`/`reply_by`/`handoff_status`/`answer_type`/`handoff`/`intent`/`citations`） |
| 流式 | 每个增量一个 `chat.completion.chunk`，末 chunk 带 `aics` 与 `usage`，随后 `data: [DONE]`；空闲沿用原生 SSE 的注释行心跳（15 s） |
| 错误体 | `{"error":{"message","type","code"}}`；`main.py` 的三个异常处理器按 `request.url.path.startswith("/v1/")` 分流，原生接口响应体一字未改（有回归用例） |

**本步发现的真实缺陷**：`JSONResponse` 直接序列化含 UUID 的 `aics` 字段会 500（Starlette 用 `json.dumps`）——改为与其它路由一致的 `jsonable_encoder`。这是单测抓到的，不是集成环境。

|---|---|---|
| 单元 `tests/unit/test_openai_api.py`（53 例） | 请求解析矩阵 | 最后一条非 user / 空 messages / 超长 / 非法 UUID / `content` 分片等拒绝分支 |

| | 路由 | 假认证器（`authenticate_key`）+ 假服务：model 不匹配 404、401/403/422 分支、限流头透传 |
| | `clamp_overrides` 矩阵 | 只收窄、非法值忽略、不污染应用配置 |

### 15.2 状态机与坐席接口（②）

| `handoff_status` × `handoff_ai_mode` | 每条 user 消息的处理（`dispatch_of`，`chat/service.py:346`） |
|---|---|
| `none` / `released` | 正常走 RAG；命中关键词 / `max_refusals` / `on_unanswerable` 则本轮转人工 |
| `pending` + `continue` | 仍走 RAG（AI 顶着答，转人工只影响坐席平台可见性） |
| `pending` + `wait` | 不调模型：写 `system/handoff_wait`（内容取 `wait_text`）并立即应答（`_run_silent_turn`） |
| `accepted` | 不调模型、不写自动回复（坐席接管中，本轮 `reply_by=none`） |

| 端点（`prefix=/api/v1/apps/{app_id}`） | scope | 说明 |
|---|---|---|
| `GET …/conversations/{id}/handoff` | `chat` 或 `handoff:write` | 状态查询，含 `in_service_hours`（由 `core.schedule.in_service_hours` 实时算，不返回假值） |
| `POST …/handoff/accept` | `handoff:write` | `pending → accepted`，记坐席与接入时间 |
| `POST …/handoff/messages` | `handoff:write` | 201；仅接入坐席本人、仅 `accepted`；写 `role=human_agent` |
| `POST …/handoff/release` | `handoff:write` | `pending` / `accepted → released`；`note` 只进日志（ISSUE-53） |
| `GET …/handoffs` | `handoff:write` | `pending` / `accepted` 队列，`id` 升序 base64url 游标 |

**为什么迁移一律是条件单行 UPDATE**：`HandoffRepository.accept/release` 的 `WHERE` 同时限定 `app_id` / `id` / 当前 `handoff_status`（交还还要求会话仍 `active`），受影响 0 行时重读数据库里的状态再抛 `409 HANDOFF_STATE_CONFLICT`（`details.handoff_status`）。先读后写会与并发的另一个坐席抢单、排队超时扫描互相覆盖；条件更新把「谁赢」交给数据库，集成用例 `test_concurrent_accept_only_one_wins` 验证两个事务同时抢单只有一个 200、另一个 409。

**坐席消息为什么不直接写 `chat.repository`**：`append_agent_message` 复用 `MessageRepository.append`，一次调用同时维护 `message_count` / `last_message_at` / `last_activity_at` 与「清 `idle_notice_sent_at`」四条联动规则；抄第二份就会漏掉其中一条，接入后无消息超时与空闲关闭会误判。

### 15.3 服务时间与三种超时（③）

| 超时 | 触发条件 | 落库结果 |
|---|---|---|
| 排队超时（§3.6） | `pending` 且 `handoff_requested_at ≤ now - handoff_queue_timeout_minutes` | `released` / `handoff_end_reason=queue_timeout` / 置待回访 / 写 `system/handoff_queue_timeout`（`queue_timeout_text`） |
| 接入后无消息（§3.8） | `accepted` 且 `last_activity_at ≤ now - handoff_accepted_idle_minutes` | `released` / `accepted_idle` / 会话 `closed` + `close_reason=handoff_idle` / 写空内容 `system/handoff_idle_closed` |
| 空闲关闭（§2，M2.7 既有） | 非 `pending` 且会话空闲超 `idle_close_minutes` | 提醒 → 关闭（`lifecycle.py`，与转人工是两个模块两套循环） |

- **幂等与并发**：两次 UPDATE 都额外比对扫描开始时读到的时间戳（`handoff_requested_at` / `last_activity_at`），不等即 0 行 → 本轮什么都不写。所以「同一轮重复扫描」「很久以后再扫」都不会重复处理，坐席在扫描与人写之间抢到的操作也不会被覆盖（集成用例各 2 条）。
- **顺序**：`idle_sweep` 先 handoff 后 lifecycle（§3.10）——会话被判定 `handoff_idle` 关闭后，lifecycle 的预筛不会再对它重复动作。
- **服务时间**：`core/schedule.py::in_service_hours(cfg, now)` 是纯函数（区间左闭右开、不跨零点、按 `zoneinfo` 本地钟面、未配置即 7×24、脏配置按不服务兜底）。放在 `core` 是因为 `chat` 与 `handoff` 都要用而两者不能互相依赖（入参用 `WeeklyHours` 结构化协议，`rag.config.ServiceHours` 天然满足）。非服务时间命中转人工时**不进队列**：会话直接 `released` + `handoff_end_reason=offline` + 待回访（`callback_reason=offline`），本轮回复换成 `system/handoff_offline`（`offline_text`、`reply_by=system`）。

### 17.2 事件与 outbox（①）

- `events.emit(session, target, type, data, *, webhook=None, occurred_at=None)` 与业务写入**同一事务**：`UPDATE conversations SET event_seq = event_seq + 1 … RETURNING event_seq` 取 `seq`（并发靠 `UNIQUE (conversation_id, seq)` 兜底），写 `conversation_events` 一行，`api` / `openai` 渠道且应用配了地址与密钥时再写一条 `webhook_deliveries`（`id` = 事件 `id`，`status='pending'`）。
- 渠道规则：`eval` 不写任何事件（评测流量不污染接入方）；`debug` 只落库不投递（排障可见、不外发）。
- `message.created` 的产生条件收在 `events.needs_message_event(role, handoff_status)`：`role=system` 或会话处于 `pending` / `accepted`——普通 AI 问答不逐条推送，事件流因此只承载「需要人看」的内容。
- 八种事件与落点：`handoff.requested` / `handoff.offline`（`chat/service.py::_write_assistant`）、`message.created`（用户消息、系统提示、AI 答复、坐席消息四处）、`handoff.accepted` / `handoff.released`（`handoff/service.py`）、`handoff.queue_timeout` / 系统释放的 `handoff.released` + `conversation.closed`（`handoff/sweep.py`）、`conversation.idle_notice` / `conversation.closed`（`chat/lifecycle.py`）。

**为什么用 `emit` 而不是在服务层各处 `session.add`**：`seq` 的分配、渠道判断、投递排队的条件必须完全一致；散在各处意味着「加一个事件点就要记得三件事」，而 `emit` 把这三件事收成一个调用。

### 17.3 会话事件流 SSE（②）

| 契约 | 实现 |
|---|---|
| `id:` | 事件的 `seq`（`Last-Event-ID` 补发的游标） |
| `data:` | 与出站 Webhook **逐字段相同**的 payload（同一份 `payloads.build_payload`） |
| 心跳 | 15 秒 `: ping`（与 `/chat` 流式共用 `HEARTBEAT_S`） |
| 结束 | 推完 `conversation.closed` 即关流（`CLOSED_EVENT`） |
| 补发 | **先 `SUBSCRIBE` 再按 `seq > Last-Event-ID` 回表读**，读满一批继续，重复靠 `seq` 去重 |
| 404 | 开流前先读会话（普通 JSON 错误体），不把 404 变成断流 |

- 不写 `event:` 行是有意的：事件名在 payload 的 `event` 字段里，浏览器默认的 `onmessage` 也能收到。
- 广播只带 `conversation_id` 与 `seq`（`PUBLISH aics:conv:{id}` → `str(seq)`），订阅方回表读全文——避免把大 payload 塞进 Redis，也让「补发」和「实时」走同一条读路径。
- **提交后广播**：`events.publish_pending(session, publisher)` 从 `session.info` 取本事务累积的 `(conversation_id, seq)`（同一会话只播最大的那个 `seq`），在 `commit()` 之后调用；发布失败只记日志（事件已落库，重连补发与重试扫描兜底）。
- **删掉了原来的 `Notify` 钩子**：`lifecycle.sweep(notify=…)` 缺 `seq`、也没有第二个调用方，M3.5 统一换成 `events.Publisher`，避免两套「提交后通知」机制走岔。

### 17.4 出站投递（③）

- 签名：`X-AICS-Signature: sha256=<hex(HMAC_SHA256(secret, timestamp + "." + body))>`，另有 `X-AICS-Event` / `X-AICS-Delivery`（= 事件 id）/ `X-AICS-Timestamp`；5 秒超时、**不跟随重定向**、2xx 即成功。
- 退避 10 s / 30 s / 2 min / 10 min / 30 min（共 6 次，`MAX_ATTEMPTS = 6`）；beat `aics.webhook_retry_sweep` 每 10 秒用 `FOR UPDATE SKIP LOCKED` 领一批（100 条）重新入队，领取后把 `next_attempt_at` 推后 60 秒防重复入队；**不用 Celery 长 `countdown`**（RabbitMQ 默认 30 分钟 `consumer_timeout` 会把长延迟消息判死）。
- 密钥：`whsec_` + 32 字节随机，Fernet（`AICS_DATA_ENCRYPTION_KEY`）加密存 `secret_enc`，明文只在生成/轮换时返回一次；投递幂等靠 `status != 'pending'` 直接 `skipped`。
- 安全：保存（`apps.service.update_app`）与每次投递（`webhooks.service`）各做一次 `core.netguard.check_url`；两次都在独立模块里调，是因为 import-linter 的独立性合同不允许 `apps` 依赖 `webhooks`（ISSUE-64）。
- `webhook/test` 的 `ping` 同步发一次、不落任何表（ISSUE-63）：`conversation_events.type` 是八值 CHECK、`webhook_deliveries.event_id` 非空唯一外键，为一条测试事件放宽约束不值；管理接口本身归 M4.5。

### 21.3 切块复核与启停

- 不属于当前生效构建号或不属于该应用 → 404 `CHUNK_NOT_FOUND`；`flagged` 不是可写值 → 422；空补丁 → 422。
